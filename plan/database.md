# CerdikPOS — Data dan pemulihan

Status: Phase 1 disetujui untuk model data logis; skema belum dipasang atau diuji. PostgreSQL di PC kafe adalah sumber kebenaran pusat. IndexedDB pada perangkat kasir menyimpan snapshot dan operasi belum tersinkron. Nota kertas adalah cadangan terakhir; tidak ada penyimpanan foto QRIS. Lihat [aturan transaksi](requirement.md) dan [kontrak HTTP](stack.md).

## Entitas dan relasi

Kecuali disebut lain, `id` bertipe UUID sebagai primary key, `*_id` adalah FK ke entitas bernama, string memakai `text`, jam server `timestamptz`, tanggal usaha `date`, nominal rupiah `bigint` nonnegatif, kuantitas/blok `integer`. Gunakan `NOT NULL` untuk data wajib dan `CHECK` untuk pilihan status/nominal/jumlah. FK riwayat memakai `RESTRICT`, bukan cascade delete. Field `?` boleh kosong; tidak ada jam rekaan ketika hanya tanggal diketahui.

**Pemetaan autentikasi.** Nama tabel/kolom di atas adalah nama logis; petakan model Better Auth dengan konfigurasi adapter, gunakan UUID konsisten untuk PK/FK termasuk ID yang dibuat library, dan hasilkan migrasi dari versi yang dikunci (termasuk plugin username). Jangan mengasumsikan daftar field ringkas ini sebagai DDL lengkap. Field `role`, `active`, `device_id`, dan `last_seen_at` hanya ditetapkan server. Jangan menerbitkan cookie sesi sebelum jalur NetBird, akun dan perangkat lulus pemeriksaan dan binding sesi berhasil; pada setiap request terlindungi cocokkan perangkat sesi dengan kredensial perangkat aktual dan periksa status terkini. Logout menghapus sesi terkait saja; reset password/nonaktif akun mencabut semua sesi akun, pencabutan perangkat menghapus sesi perangkat serta memblokir akses lewat status perangkat. Penggantian perangkat kasir mengubah status perangkat dan audit dalam satu transaksi; pencabutan sesi harus tuntas sebelum akses baru dibuka, atau status lama harus tetap memblokir akses. Tidak ada penghapusan akun historis; FK bisnis RESTRICT. FK internal autentikasi mengikuti skema resmi jika tidak bertentangan dengan aturan tersebut. Tidak menambah adapter digest atau service database lain. Backend Fastify dan Better Auth menggunakan `pg` (node-postgres) dalam satu aplikasi; gunakan pool koneksi dengan role runtime berhak minimum untuk autentikasi dan domain. Pisahkan role migrasi dan backup. Tidak ada akses DB dari klien. Satu runner migrasi SQL meninjau dan menerapkan skema hasil generate Better Auth bersama migrasi domain TypeScript; jangan menjalankan dua migrator bersamaan. Field email internal unik yang diperlukan plugin username bukan alamat kontak, tidak digunakan untuk pengiriman email. Referensi: [Database](https://better-auth.com/docs/concepts/database), [Username](https://better-auth.com/docs/plugins/username), [Session management](https://better-auth.com/docs/concepts/session-management).

**Pemetaan nota ke DB.** `record.occurred_date` menjadi `paper_notes.note_date`. `sales.business_date` memakai tanggal jual tunai atau tanggal bukti QRIS dalam zona saat kejadian, bukan `entered_at`. `link` mengambil field wajib yang tidak dikirim dari penjualan cocok; simpan alasan dan bukti tautan. `discrepancy` membuat nota dan kasus dalam satu commit tanpa `sale_id`; `cases.original_request_id` opsional untuk pencarian O-04. Jika bukti menyusul, kunci nota dan kasus, audit snapshot lama, lalu tautkan atau catat penjualan terbukti satu kali pada nota yang sama. Kasus yang memerlukan keputusan direktur tetap terbuka sampai keputusan tersebut; tidak ada izin untuk menimpa nota yang sudah selesai.

**Pagar untuk request terlambat.** Jika nota yang dibukukan merujuk ID percobaan langsung, reservasi ID asal dan ID input susulan pada `request_receipts` dalam commit yang sama; keduanya merujuk satu hasil. Jika ID asal telah terpakai, periksa hasilnya dan cocokkan, jangan sisipkan penjualan kedua. Jika request langsung tiba kemudian, kembalikan rujukan hasil yang boleh dilihat atau konflik untuk pemeriksaan, tanpa efek baru. Nomor nota, ID asal dan receipt tidak menggantikan bukti saat restore kehilangan sebagian riwayat.

**Pemulihan meja.** Saat serah terima dari nota ke aplikasi, tandai meja yang belum diperiksa `needs_check` sebelum menerima alokasi baru untuk meja tersebut. Aksi pencocokan mengunci baris meja, memeriksa status fisik terhadap sesi/nota dan merekam alasan serta aktor. Hanya hasil cocok menghapus penanda; meja yang bersih tetapi belum dilepas manual tidak menjadi tersedia karena pencocokan.
## Model lokal IndexedDB (Dexie) dan penerimaan sinkron

| Store lokal | Isi minimum |
|---|---|
| `offline_context` | `grant_id,device_id,snapshot_id,issued_at,expires_at,server_time,sequence,schema_version`, daftar petugas yang dibekukan untuk grant, `active_cashier_id?` dan generasi penguncian. Satu context perangkat; durasi maksimal 7 hari, bukan tujuh hari per petugas. |
| `cashier_unlock` | Per `device_id,user_id,preparation_id`: verifier PIN ber-salt dan status pembatasan percobaan; hanya lokal. Bukan PIN asli, bukan token sesi; tidak masuk outbox, ekspor transaksi, log atau backup PostgreSQL. |
| `catalog_snapshot` | SKU, nama, kategori, harga, status, versi stok, tarif, zona dan durasi pembersihan |
| `stock_projection`, `rental_projection` | saldo lokal, status meja/sesi, UUID rental lokal, batas waktu dan versi dasar |
| `operations` | `request_id` UUID unik, `grant_id`, sequence unik per grant, `original_cashier_id`, jenis, payload immutable, waktu kejadian, tanggal usaha, status, attempts, last_error?, receipt?, created_at. Event `cashier_switch` berisi identitas sebelumnya/berikutnya dan tidak mempunyai efek pembayaran, stok atau sewa. |
| `sync_meta` | waktu ack terakhir, server epoch, lease pengirim, indikator recovery |

Gunakan transaksi Dexie readwrite mencakup context, operation dan proyeksi terdampak; cek stok, status meja, izin dan sequence di dalam transaksi, bukan hanya UI. Jika gagal/quota penuh jangan tampilkan sukses. Jangan melakukan HTTP di dalam transaksi IndexedDB. Simpan request ID sebelum pengiriman; ack dan perubahan status atomik. Pada restart, perbaiki status `syncing` menjadi `pending` tanpa ID baru. Rebuild proyeksi dari snapshot dan operasi yang belum tercakup, bukan menerapkan pengurangan stok dua kali. Pertahankan payload dan receipt tersinkron sesuai retensi recovery; jangan hapus pending saat logout atau migrasi.

Saat **Ganti kasir** atau logout, kunci context dan naikkan generasinya agar semua tab kehilangan hak petugas lama. PIN yang salah tidak memulihkan identitas lama. Setelah PIN benar, periksa ulang grant dan roster lalu aktifkan petugas dan simpan event pergantian dalam satu transaksi lokal. Saat menjual, cocokkan generasi dan identitas layar dengan context di dalam transaksi tulis; tab lama harus diblokir, bukan diam-diam menjual atas nama petugas baru. Reload mengunci layar; membuka kembali dengan PIN tidak menghapus antrean atau memperbarui tenggat.

Tambahan PostgreSQL:

- `offline_grants`: UUID, `opened_by`, device_id, snapshot_id, issued_at, expires_at, closed_at?, revoked_at?, last_sequence. Satu grant terbuka per perangkat; batas server maksimal 168 jam. Daftar izin direktur dan persiapan online tersimpan per perangkat/pengguna; `offline_grant_cashiers(grant_id,user_id,preparation_id)` membekukan keanggotaan ketika grant dibuka. Grant expired tetap mengunci master terkait sampai close/recovery. Snapshot historis dan penerbitan grant mengikuti lock yang sama dengan perubahan master.
- `request_receipts`: tambah grant_id?, sequence?, result_status; unik parsial `(grant_id,sequence)` dan `request_id` unik global. Persistensikan `original_cashier_id` per operasi, tervalidasi terhadap roster dan riwayat aktivasi (untuk aktivasi awal gunakan petugas pembuka yang telah disiapkan). `sales.entered_by` adalah pengirim/pemulih online, bukan pengganti kasir asal. Pergantian, receipt, efek bisnis bila ada, sequence dan audit mengikuti satu commit server.
- `sync_recovery`: status gate dan epoch server (epoch baru saat restore terkontrol); tahan replay hingga pencocokan. Receipt yang hilang setelah restore tidak boleh dianggap tidak pernah ada. Gunakan operasi lokal/receipt tersimpan, nota, kas dan stok fisik sebagai bukti; rekonstruksi hanya setelah keputusan berwenang, audit, dan ID asli.
- FIFO: lock grant, cek receipt sebelum sequence berikutnya dan dependensi rental. UUID rental lokal stabil dipakai sebagai ID server atau dipetakan secara unik. Saat status `needs_review`, hentikan pengiriman berikutnya sampai keputusan berwenang; receipt membuktikan hasil pemeriksaan tercatat, bukan semua efek bisnis berhasil. Pembayaran terbukti dengan selisih stok dicatat sekali; baris stok bermasalah tidak dipaksakan. Jika pembayaran atau otorisasi sendiri tidak terbukti, simpan bukti/kasus di luar omzet final. Tutup grant hanya setelah seluruh sequence dicocokkan dengan perangkat, atau recovery manual untuk perangkat hilang.


## Integritas dan alur penyimpanan

Gunakan satu client `pg` yang diperoleh dari pool untuk setiap transaksi (`BEGIN`/`COMMIT`/`ROLLBACK`); lepaskan client dalam `finally`. Jangan mencampur query pool dengan client transaksi. Validasi payload menggunakan Zod strict di server. PostgreSQL `bigint` dibaca sebagai string/BigInt tanpa kehilangan presisi; konversi ke angka JSON hanya dalam rentang integer aman. Tanggal usaha `date` ditangani sebagai tanggal kalender, bukan timestamp yang bergeser zona.

1. **Langsung.** Di satu transaksi DB: periksa ulang status akun/perangkat dan hak bisnis yang relevan, identitas request dan tarif/harga yang dikonfirmasi; kunci baris produk menurut urutan ID atau baris meja/sesi; validasi saldo/status; simpan penjualan, pembayaran, movement/event, receipt dan audit. `amount=total`; tunai `cash_received>=amount` dan kembalian selisihnya; untuk QRIS field tunai null dan pemeriksaan bukti wajib. Rollback seluruh operasi yang gagal. Untuk QRIS yang telanjur dibayar namun tidak terpenuhi, catat pembayaran dan pengecualian dalam satu commit, bukan klaim layanan selesai.
2. **Benturan dan replay.** ID percobaan stabil dibuat sebelum Simpan, indeks unik DB menserialisasi dua kiriman. Identitas, operasi dan isi sama mengembalikan hasil tersimpan; isi berbeda konflik. Pengulangan nomor nota lewat ID baru tidak membuat pembayaran baru. Pencocokan dengan percobaan asal harus memakai kunci ID asal yang sama dengan jalur langsung sehingga commit terlambat tidak menghasilkan dua penjualan. Jangan memutuskan transaksi tidak pernah terjadi hanya dari hasil pencarian kosong setelah restore; simpan kasus hingga bukti cukup.
3. **Penjualan susulan.** Kunci nomor nota, cocokkan nota atau penjualan lama terlebih dahulu. Untuk `link`, hanya simpan tautan dan audit. Untuk `record`, simpan nilai historis dan pembayaran satu kali. Kurangi hanya stok baris yang dapat dipastikan dan belum tercatat; bila SKU nonaktif/tidak dikenal, saldo kurang, atau hitung fisik sudah mencakup barang yang keluar, tandai baris untuk rekonsiliasi, bukan stok minus atau pembayaran kedua. Saat menutup kasus, catat apakah pengeluaran dibukukan, sudah tercakup hitung fisik, atau dikoreksi dengan movement beralasan. Jika pembayaran sendiri tidak dapat dibuktikan, buat selisih tanpa penjualan final.
4. **Sewa.** Unik parsial `rentals(table_id)` untuk sesi operasional yang belum dilepas (aktif/pembersihan). Cek benturan waktu dan alokasi dalam transaksi dengan lock meja; indeks unik saja tidak memvalidasi urutan event. Penambahan blok hanya sebelum habis dan memakai `paid_until` lama. Pembersihan dimulai dari penutupan dini atau batas akhir normal; jika waktu server tidak tepercaya, blokir aksi yang bergantung pada waktu sampai diperiksa. Kadaluwarsa dihitung dari batas server tanpa job per detik; lepas manual setelah `clean_until`. Nota sesi selesai merekam timeline tanpa menggeser meja saat ini; sesi yang masih berjalan hanya dipulihkan setelah cocok meja fisik dan waktu asli. Benturan atau bukti waktu tidak cukup masuk kasus, tidak mengubah sesi lain.
5. **Verifikasi, refund dan laporan.** `pending_date` tidak masuk penjualan final. Simpan `proof_date` walau `proof_at` kosong. Verifikasi mengubah proyeksi pembukuan, tidak membuat pembayaran lain. Kunci penjualan saat mengecek jumlah refund kumulatif. Agregasi penjualan dan refund secara terpisah menurut tanggal masing-masing sebelum digabung untuk menghindari duplikasi akibat join. Tanggal tersimpan tidak berubah hanya karena zona usaha diganti. Dashboard/CSV memakai query agregasi yang sama; laporan historis bisa terbarui setelah input nota.
6. **Indeks sesuai akses.** Selain PK/FK yang banyak dipakai dan constraint unik: `sales(business_date,booking_state)`, `refunds(returned_date)`, `stock_movements(product_id,recorded_at)`, kasus terbuka dan `audit_events(entity_type,entity_id,recorded_at)`. Tambah indeks lain berdasarkan query dan data uji, bukan dugaan kapasitas.

## Siklus data, migrasi dan recovery

- Inisialisasi database kosong dengan migrasi SQL bernomor yang tercatat di `schema_migrations`; sertakan migrasi Better Auth yang dihasilkan dan ditinjau dalam urutan migrasi yang sama; buat akun awal melalui jalur lokal terkontrol menggunakan mekanisme kredensial Better Auth, bukan password mentah atau hash buatan sendiri. Muat data awal kafe melalui operasi master/stok yang diaudit; saldo awal adalah movement, bukan edit angka tanpa riwayat.
- Setiap perubahan skema mengikuti versi aplikasi dan diuji terhadap DB kosong serta salinan versi sebelumnya. Sebelum migrasi operasional, cek backup dan kemampuan restore di media terpisah. Jangan jalankan migrasi destruktif atau hapus data riil sebagai bagian fase perencanaan.
- Penjualan, pembayaran, nota, movement dan audit dipertahankan; tidak ada penghapusan permanen dari UI. Kebijakan retensi operasional/backup dan pemusnahan nota kertas diatur kafe sebelum serah terima. Akun/produk dinonaktifkan tanpa memutus histori.
- Direktur bertanggung jawab atas backup PostgreSQL terjadwal ke media terpisah dan pemulihan PC. Backup terproteksi, catat waktu backup terakhir yang sukses. Pulihkan ke instance terisolasi, validasi migration, transaksi terakhir, total per hari/metode, saldo, meja dan akses. Setelah penggantian, pastikan hanya satu server menerima penulisan. Sebelum membuka akses, hapus seluruh sesi autentikasi dan undangan enrollment yang dipulihkan; cocokkan akun/perangkat dengan catatan operasional tepercaya, cabut kembali yang telah dicabut dan reset kredensial yang berubah setelah backup. Jika status tidak dapat dibuktikan, tahan akses akun/perangkat tersebut sampai diregistrasi atau diverifikasi ulang. Lindungi token sesi, hash password dan secret dalam backup.
- Cocokkan transaksi **setelah titik salinan terakhir, sebelum server mati** dengan bukti yang masih tersedia. Untuk transaksi **selama server mati**, gunakan antrean IndexedDB atau nota jika perangkat gagal. Backup PostgreSQL tidak mencakup antrean tersebut. Pertahankan perangkat kasir dan origin HTTPS saat restore; jangan hapus data browser. Uji kehilangan perangkat, quota, penghapusan browser dan rekonsiliasi nota/kas. Jika bukti hilang, catat selisih; jangan membukukan ulang tanpa bukti.

## Backup harian dan pemulihan server

- **Jadwal:** jalankan backup PostgreSQL otomatis setiap hari pukul **04.00 WITA** (`Asia/Makassar`) tanpa menghentikan aplikasi atau database. Jika jadwal terlewat karena listrik padam, jalankan segera setelah server dan media backup siap, tanpa menunggu besok. Simpan salinan terenkripsi di media terpisah dari PC server.
- **Ketersediaan:** target nol gangguan. Bila backup mengganggu layanan pusat, ukur dari kegagalan pertama sampai akses database dan layanan sinkronisasi kembali berfungsi; batas **5 menit per kejadian**. Durasi pembuatan salinan boleh lebih lama. Kasir yang tetap bisa mencatat offline tidak berarti layanan pusat sudah pulih.
- **Setiap selesai backup:** periksa hasil proses dan pastikan salinan di media tujuan lengkap dan dapat dibaca. Periksa juga database operasional dan respons layanan sinkronisasi. Catat waktu, hasil salinan dan kondisi layanan secara terpisah. Jika pemeriksaan gagal, beri tahu direktur; jangan ganti salinan terakhir yang baik dengan salinan gagal.
- **Sebulan sekali:** pulihkan salinan ke database uji terisolasi, bukan ke database kasir. Cocokkan transaksi terakhir dan total per tanggal/metode dengan catatan untuk titik backup yang sama. Catat hasil; laporkan kegagalan ke direktur. File yang dapat dibaca belum membuktikan datanya bisa dipulihkan.
- **Jika PC rusak:** target layanan pusat dapat digunakan kembali dalam **2 jam sejak listrik, PC pengganti dan backup siap**. Catat waktu gangguan pertama, kesiapan ketiga prasyarat dan waktu layanan dibuka dengan aman. Laporkan durasi pemulihan dan total gangguan termasuk waktu tunggu. Jangan membuka sinkronisasi sebelum pemeriksaan direktur selesai. Buktikan target melalui simulasi di lokasi.
- **Jarak data:** titik pemulihan adalah titik data pada salinan terakhir yang berhasil, bukan waktu pengecekan file. Dengan backup harian normal, hampir 24 jam transaksi pusat mungkin perlu dicocokkan ulang; kegagalan backup bisa memperpanjang jarak ini. Tidak ada jaminan nol kehilangan data.
