# CerdikPOS — Data dan pemulihan

Status: revisi opsi B, bukan skema terpasang. PostgreSQL adalah database utama dan sumber laporan. IndexedDB di satu perangkat kasir menyimpan salinan kerja dan transaksi offline sampai server mengakui commit. Nota kertas adalah cadangan bila PWA tidak dapat mencatat. Foto QRIS berada di luar keduanya. Lihat [aturan transaksi](requirement.md) dan [kontrak HTTP](stack.md).

## Entitas dan relasi

Kecuali disebut lain, `id` bertipe UUID sebagai primary key, `*_id` adalah FK ke entitas bernama, string memakai `text`, jam server `timestamptz`, tanggal usaha `date`, nominal rupiah `bigint` nonnegatif, kuantitas/blok `integer`. Gunakan `NOT NULL` untuk data wajib dan `CHECK` untuk pilihan status/nominal/jumlah. FK riwayat memakai `RESTRICT`, bukan cascade delete. Field `?` boleh kosong; tidak ada jam rekaan ketika hanya tanggal diketahui.

| Tabel | Field inti dan hubungan |
|---|---|
| `users`, `devices`, `sessions` | Pengguna: `username` unik, `name`, `role`, `password_hash`, `active`. Perangkat: `label`, `kind`, `credential_digest?`, `registered_by`, `revoked_at?`, `active_cashier boolean`. Sesi: `user_id`, `device_id`, `token_digest` unik, `expires_at`, `revoked_at?`. Indeks unik parsial menjamin maksimal satu perangkat kasir aktif; tidak membatasi sesi direktur pada perangkat terdaftar lain. |
| Pendaftaran dan masa sesi | Pada `devices`: `enrollment_digest?`, `enrollment_expires_at?`; `credential_digest` kosong sebelum penukaran. Tukar token sekali secara atomik, hapus digest undangan, simpan digest kredensial perangkat tujuan. Pada `sessions`: `last_seen_at` untuk idle timeout; `expires_at` adalah batas absolut. Akun kasir nonaktif tetap dapat dirujuk sebagai petugas asal. |

**Pemetaan nota ke DB.** `record.occurred_date` menjadi `paper_notes.note_date`. `sales.business_date` memakai tanggal jual tunai atau tanggal bukti QRIS dalam zona saat kejadian, bukan `entered_at`. `link` mengambil field wajib yang tidak dikirim dari penjualan cocok; simpan alasan dan bukti tautan. `discrepancy` membuat nota dan kasus dalam satu commit tanpa `sale_id`; `cases.original_request_id` opsional untuk pencarian O-04. Jika bukti menyusul, kunci nota dan kasus, audit snapshot lama, lalu tautkan atau catat penjualan terbukti satu kali pada nota yang sama. Kasus yang memerlukan keputusan direktur tetap terbuka sampai keputusan tersebut; tidak ada izin untuk menimpa nota yang sudah selesai.

**Pagar untuk request terlambat.** Jika nota yang dibukukan merujuk ID percobaan langsung, reservasi ID asal dan ID input susulan pada `request_receipts` dalam commit yang sama; keduanya merujuk satu hasil. Jika ID asal telah terpakai, periksa hasilnya dan cocokkan, jangan sisipkan penjualan kedua. Jika request langsung tiba kemudian, kembalikan rujukan hasil yang boleh dilihat atau konflik untuk pemeriksaan, tanpa efek baru. Nomor nota, ID asal dan receipt tidak menggantikan bukti saat restore kehilangan sebagian riwayat.

**Pemulihan meja.** Saat serah terima dari nota ke aplikasi, tandai meja yang belum diperiksa `needs_check` sebelum menerima alokasi baru untuk meja tersebut. Aksi pencocokan mengunci baris meja, memeriksa status fisik terhadap sesi/nota dan merekam alasan serta aktor. Hanya hasil cocok menghapus penanda; meja yang bersih tetapi belum dilepas manual tidak menjadi tersedia karena pencocokan.
## Integritas dan alur penyimpanan

1. **Langsung.** Di satu transaksi DB: periksa hak, identitas request dan tarif/harga yang dikonfirmasi; kunci baris produk menurut urutan ID atau baris meja/sesi; validasi saldo/status; simpan penjualan, pembayaran, movement/event, receipt dan audit. `amount=total`; tunai `cash_received>=amount` dan kembalian selisihnya; untuk QRIS field tunai null dan pemeriksaan bukti wajib. Rollback seluruh operasi yang gagal. Untuk QRIS yang telanjur dibayar namun tidak terpenuhi, catat pembayaran dan pengecualian dalam satu commit, bukan klaim layanan selesai.
2. **Benturan dan replay.** ID percobaan stabil dibuat sebelum Simpan, indeks unik DB menserialisasi dua kiriman. Identitas, operasi dan isi sama mengembalikan hasil tersimpan; isi berbeda konflik. Pengulangan nomor nota lewat ID baru tidak membuat pembayaran baru. Pencocokan dengan percobaan asal harus memakai kunci ID asal yang sama dengan jalur langsung sehingga commit terlambat tidak menghasilkan dua penjualan. Jangan memutuskan transaksi tidak pernah terjadi hanya dari hasil pencarian kosong setelah restore; simpan kasus hingga bukti cukup.
3. **Penjualan susulan.** Kunci nomor nota, cocokkan nota atau penjualan lama terlebih dahulu. Untuk `link`, hanya simpan tautan dan audit. Untuk `record`, simpan nilai historis dan pembayaran satu kali. Kurangi hanya stok baris yang dapat dipastikan dan belum tercatat; bila SKU nonaktif/tidak dikenal, saldo kurang, atau hitung fisik sudah mencakup barang yang keluar, tandai baris untuk rekonsiliasi, bukan stok minus atau pembayaran kedua. Saat menutup kasus, catat apakah pengeluaran dibukukan, sudah tercakup hitung fisik, atau dikoreksi dengan movement beralasan. Jika pembayaran sendiri tidak dapat dibuktikan, buat selisih tanpa penjualan final.
4. **Sewa.** Unik parsial `rentals(table_id)` untuk sesi operasional yang belum dilepas (aktif/pembersihan). Cek benturan waktu dan alokasi dalam transaksi dengan lock meja; indeks unik saja tidak memvalidasi urutan event. Penambahan blok memakai `paid_until` lama. Kadaluwarsa dihitung dari batas server tanpa job per detik; lepas manual setelah `clean_until`. Nota sesi selesai merekam timeline tanpa menggeser meja saat ini; sesi yang masih berjalan hanya dipulihkan setelah cocok meja fisik dan waktu asli. Benturan atau bukti waktu tidak cukup masuk kasus, tidak mengubah sesi lain.
5. **Verifikasi, refund dan laporan.** `pending_date` tidak masuk penjualan final. Simpan `proof_date` walau `proof_at` kosong. Verifikasi mengubah proyeksi pembukuan, tidak membuat pembayaran lain. Kunci penjualan saat mengecek jumlah refund kumulatif. Agregasi penjualan dan refund secara terpisah menurut tanggal masing-masing sebelum digabung untuk menghindari duplikasi akibat join. Tanggal tersimpan tidak berubah hanya karena zona usaha diganti. Dashboard/CSV memakai query agregasi yang sama; laporan historis bisa terbarui setelah input nota.
6. **Indeks sesuai akses.** Selain PK/FK yang banyak dipakai dan constraint unik: `sales(business_date,booking_state)`, `refunds(returned_date)`, `stock_movements(product_id,recorded_at)`, kasus terbuka dan `audit_events(entity_type,entity_id,recorded_at)`. Tambah indeks lain berdasarkan query dan data uji, bukan dugaan kapasitas.

### Penyimpanan PWA dan penerimaan event

- IndexedDB: simpan snapshot kerja berversi, acuan waktu server, identitas izin offline, proyeksi stok/meja dan `outbox` berisi envelope event pada [kontrak API](stack.md). Saat kasir menyimpan, baca ulang status lokal dan cek stok/meja dalam satu transaksi read-write lintas store; simpan event immutable, urutan per perangkat, pembayaran/aksi sewa, perubahan proyeksi dan identitas audit bersama. Sukses baru setelah transaksi IndexedDB selesai, bukan saat request tulis pertama berhasil. Kegagalan membatalkan semua efek. Dua tab tidak boleh menjual saldo atau meja terakhir dua kali.
- Saat online, buat ID sebelum mengirim dan simpan penanda percobaan sampai hasil pasti. Penanda **bukan** pembayaran lokal atau perintah kirim otomatis sebagai penjualan baru. Jika respons hilang, gunakan ID itu untuk memeriksa/mengulang operasi asal. Jangan izinkan snapshot usang atau hasil belum pasti membuka stok/meja yang sama untuk alokasi lain.
- Grant PostgreSQL dimiliki perangkat untuk maksimal 7 hari; daftar petugas yang telah disiapkan dibekukan saat izin diterbitkan. Pada tiap operasi simpan `original_cashier_id` tetap; kasir yang mengirim/memulihkan dicatat terpisah. Pergantian lokal mengunci semua tab lama sebelum mengaktifkan petugas baru, menggunakan sequence yang sama tanpa mereset saldo/meja atau antrean. `cashier_switch` tidak mengubah uang, stok atau sewa. Server memvalidasi roster, urutan, nominal dan snapshot lalu menyimpan receipt, efek bisnis atau kasus serta audit bersama. Lihat [model utama](../cerdikpos-offline-first_UPDATE/database.md) untuk verifier PIN lokal, data grant dan validasi pergantian.
- Hapus event dari antrean aktif hanya setelah receipt server yang cocok dicatat lokal; jika crash sebelum itu, kirim ulang ID yang sama. Setelah antrean diproses, muat snapshot server, kemudian lanjutkan mutasi online. Jangan menerapkan perpanjangan sebelum event mulai sesi. Rekonsiliasi meja bermasalah menggunakan kondisi fisik, bukan memulai ulang timer.

## Siklus data, migrasi dan recovery

- Inisialisasi database kosong dengan migrasi SQL bernomor yang tercatat di `schema_migrations`; buat akun awal melalui jalur lokal terkontrol. Muat data awal kafe melalui operasi master/stok yang diaudit; saldo awal adalah movement, bukan edit angka tanpa riwayat.
- Setiap perubahan skema mengikuti versi aplikasi dan diuji terhadap DB kosong serta salinan versi sebelumnya. Sebelum migrasi operasional, cek backup dan kemampuan restore di media terpisah. Jangan jalankan migrasi destruktif atau hapus data riil sebagai bagian fase perencanaan.
- Penjualan, pembayaran, nota, movement dan audit dipertahankan; tidak ada penghapusan permanen dari UI. Kebijakan retensi operasional/backup dan pemusnahan nota kertas diatur kafe sebelum serah terima. Akun/produk dinonaktifkan tanpa memutus histori.
- Direktur bertanggung jawab atas backup PostgreSQL terjadwal ke media terpisah dan pemulihan PC. Backup terproteksi, catat waktu backup terakhir yang sukses. Pulihkan ke instance terisolasi, validasi migration, transaksi terakhir, total per hari/metode, saldo, meja dan akses. Setelah penggantian, pastikan hanya satu server menerima penulisan. Periksa kredensial/sesi/perangkat yang dicabut setelah backup dan cabut kembali sebelum membuka akses.
- Backup PostgreSQL tidak mencakup antrean lokal. Saat server belum pulih pada ganti shift/tutup kas atau sebelum mengganti perangkat, ekspor antrean terenkripsi ke media terpisah; simpan frasa sandi di luar perangkat. Saat pulih, impor melalui perangkat aktif dengan autentikasi; pertahankan ID, urutan, pencatat, perangkat asal dan nilai historis. Arsip rusak, frasa salah atau replay tidak boleh memunculkan penjualan ganda. Cocokkan juga nota cadangan serta transaksi setelah backup server terakhir. Tanpa data/ekspor atau bukti lain, catat selisih; jangan mengklaim data pulih. RPO/RTO, retensi dan pemegang frasa darurat belum ditetapkan.
